<p>很多人测节点只做一件事：ping 一下，通就下单。这个动作能筛掉的只有彻底不通的地址，剩下的问题要等用起来才暴露——白天好好的，晚上八点开始超时；单次请求很快，连续跑十分钟开始丢包。节点质量是个随时间变化的量，按时间轴分五段测，每段看不同指标，比一口气测完更接近真实使用。</p>

<h2>一、T+0 的三分钟：先筛掉一半候选</h2>
<p>开场只做粗筛，目标是快速淘汰，不做精测。先把候选地址列出来，逐条打一次延迟、一次路由，再看首字节时间。这一轮不需要精确，只需要一个「明显不行」的判断，把候选从十条压到三五条。</p>
<h3>ping 不够用，要看 mtr 的三跳</h3>
<p>ping 只告诉你往返时间，不告诉你卡在哪一跳。用 mtr --report -c 100 目标地址，看第 3 到第 8 跳的丢包分布：如果中间某跳开始丢且后续跳延续，问题在那段链路；如果最后一跳才丢，问题在出口本身。再配合 curl -o /dev/null -s -w "%{time_connect} %{time_starttransfer} %{time_total}" 看连接、首字节、总耗时三段的比例。</p>

<h2>二、T+10 分钟：从「能通」到「够稳」</h2>
<p>粗筛过后进入短时压测，看的是波动而非均值。均值 120 毫秒、波动范围 100 到 900 毫秒的节点，观感会比均值 180 毫秒、稳定在 170 到 200 毫秒的节点差很多，因为交互类业务对尾延迟的敏感度远高于均值。</p>
<h3>抖动和丢包要分开算</h3>
<p>抖动看的是相邻样本的差值，网络抖动大意味着交互体感卡顿；丢包看的是失败比例，丢包高意味着重传多、有效吞吐下降。两个指标要分别记录：把 50 次请求的耗时排序，取第九十五百分位作为尾延迟，再单独统计失败次数。尾延迟超过均值三倍，说明存在周期性拥塞。</p>

<h2>三、20:00 到 23:00：晚高峰才是真实水平</h2>
<p>白天测出来的数据普遍好看，因为国际链路和住宅上行在夜间都更拥挤。同一个节点，下午三点测 90 毫秒，晚上九点可能变成 400 毫秒加 8% 丢包。所以真正的验收窗口是本地时间晚上八点到十一点，这个时段的数字才决定日常体验。</p>

<h2>四、连续 7 天：看的是波动，不是均值</h2>
<p>一天的数据只能说明当时的状态，一周的数据才能看出规律。连续七天、每小时抽一次，把每次的延迟、丢包、可用率记下来，重点看两件事：每天同一时段是否重复出现劣化、劣化是否与特定路由节点相关。重复出现的劣化是线路问题，偶发的是拥塞。</p>
<h3>记录表留哪几列</h3>
<p>时间、节点标识、往返延迟、丢包率、首字节时间、是否失败。六列足够，多记反而没人填。七天之后按小时聚合，画出两条线：延迟的分位曲线和失败次数，规律一眼就能看出来。</p>

<h2>五、第 30 天：决定续费还是替换</h2>
<p>一个月的数据才有商业意义，因为它跨过了计费周期和至少一次运维事件。这时候要回答的不是「快不快」，而是「值不值」：可用率是否达到承诺、故障恢复是否在约定时限内、替换流程是否真的走通了。</p>
<h3>替换的判定线怎么画</h3>
<p>建议提前定三条硬线：晚间可用率低于 95% 累计超过三天、单次故障超过 30 分钟且当月出现两次以上、替换申请超过约定时限未处理。任一条命中就进替换流程，不靠临场感觉。定线的好处是避免「再用一周看看」拖成三个月。</p>

<h2>常见问答</h2>
<h3>只测 ping 能不能判断节点好坏？</h3>
<p>答：不够。ping 走的是 ICMP，很多线路对 ICMP 有优先级处理，结果偏乐观。真实业务走 TCP，要用 TCP 层的握手时间和首字节时间来测才准确。</p>
<h3>夜间测出来的数据很差，是不是节点不行？</h3>
<p>答：不一定，先看是本地出口拥塞还是对方链路拥塞。用同一时段对比两三个不同运营商的本地网络，如果都差，问题多半在远端；只有一个差，先查本地。</p>
<h3>需要专业工具吗？</h3>
<p>答：起步阶段不需要。mtr、curl、nc 三个命令加一张表就能完成大部分判断。等到要长期监测多节点时，再考虑上探针或现成的监测服务。</p>
<h3>测多久才够决定采购？</h3>
<p>答：粗筛三分钟、短测十分钟、晚高峰一小时、连续七天、满月复盘。前两步可以当天做完，决定长期合作建议看到七天数据。</p>
